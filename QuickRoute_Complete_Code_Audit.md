## 1. Project Idea in Simple Terms

QuickRoute is meant to be a building-agnostic indoor wayfinding system. An end user scans or types a code at a kiosk/entrance, which resolves to an exact starting point inside a specific building/map; they then pick a destination room, the backend runs Dijkstra over an admin-drawn graph of `RoutePoint`/`RouteEdge` documents scoped to that map, and the frontend overlays the resulting path on the map's own uploaded image using the image's native pixel coordinates. Admins manage buildings, rooms, maps (image or PDF upload, auto-processed into a clean "display" map plus an accurate "source" map), draw the walkable graph directly on the map, link entrances/rooms/stairs/elevators into that graph, test routes before publishing, and issue invitation codes that gate signup by role and building scope (`super_admin`, `global_manager`, `building_manager`, `regular_user`).

## 2. Current Architecture

**Frontend** (`frontend/src`, React 19 + Vite, JavaScript, no TypeScript): `App.jsx` is a single `BrowserRouter` with numbered end-user screens (`/screen/01`…`/screen/18`) plus dedicated `/admin/*` routes, all wrapped in `LocationProvider → LangProvider → AuthProvider → AdminProvider`. Every screen is a self-contained `.jsx` file under `screens/` with its own inline `UI` translation dictionary (en/ar/he) — there is no shared i18n library. Small presentational pieces live in `components/`. All backend I/O goes through `api/*.js` modules, each a thin wrapper around one FastAPI router.

**Frontend auth:** `context/AuthContext.jsx` holds the logged-in user in React state, seeded from and persisted to `localStorage["quickroute_user"]`, plus a JWT in `localStorage["quickroute_token"]`. `api/api.js`'s `apiRequest()` helper reads the token directly from `localStorage` (not from React context) so it can attach `Authorization: Bearer <token>` to every JSON request, and clears both storage keys on a `401`. `components/RequireRole.jsx` is the client-side route guard used around every `/admin/*` route and `/screen/05`.

**Backend** (`backend/`, FastAPI + Beanie ODM + MongoDB Atlas): `app.py` builds the `FastAPI` app, mounts `StaticFiles` at `/uploads` for generated map images, registers 8 routers, and its `lifespan` hook calls `database/mongo.py:init_db()`, which loads `MONGO_URI`/`DATABASE_NAME` from `backend/.env` (falling back to `mongodb://localhost:27017` / `quickroute_db` only if the env var is absent) and calls `init_beanie()` against all 8 document models. JWT creation/decoding and password hashing live in `core/security.py`; the `Authorization` header → `User` document resolution and role/building-scope checks live in `core/auth_deps.py`. Route files under `routes/` are thin: they validate input, call `core/auth_deps.py` dependencies for permission checks, and talk to Beanie models directly (there's no separate repository/service layer except for maps, which has `logic/`, `services/map_image_service.py`, and `services/storage_backend.py`).

**Data relationships:** `Building 1—* Room`, `Building 1—* RoutePoint` (via `building_id`), `Map 1—* RoutePoint` and `Map 1—* RouteEdge` (via `map_id`), `Room 0—* RoutePoint` (a RoutePoint optionally represents a room's entry point via `room_id`), `RouteEdge *—2 RoutePoint` (`from_point_id`/`to_point_id`), `LocationCode 1—1 RoutePoint` (a scanned code always resolves to exactly one starting `RoutePoint`) plus `building_id`/`map_id` for consistency checks, `InvitationCode 1—1 User` (consumed once on signup, carries the role/building scope the new user inherits).

**Map upload/serving:** `POST /api/maps/upload` (multipart) saves the file to `backend/uploads/maps/temporary/`, inserts a `Map` document with `processing_status="pending"`, and immediately returns — the actual PDF/image normalization, local "display map" generation (OpenCV-based wall/room segmentation, `services/map_image_service.py`), and optional OpenAI-based colorization run in a `BackgroundTasks` job. Finished files land in `backend/uploads/maps/source/{id}.png` and `.../display/{id}.png`, served at `/uploads/maps/...` via the mounted `StaticFiles`. `services/storage_backend.py` optionally re-uploads the same files to S3 when `MAP_STORAGE_BACKEND=s3` and swaps the stored URL — this is a no-op by default.

**Route drawing → graph data:** In `AdminMapScreen.jsx`, "Draw Walkable Path" mode collects click points into a local `draftPoints` array (never touching the backend mid-draw), then `handleSaveDraft()` (lines 1263–1399) creates a `RoutePoint` for each new draft vertex and a bidirectional `walkway` `RouteEdge` between consecutive vertices via `createRoutePoint`/`createRouteEdge`, with client-side de-duplication of already-existing edges and a rollback path that deletes everything it just created if any step fails. Clicking an existing point in "Add Point" mode can optionally auto-connect it to the nearest point on the same floor (`connectToNearest`, lines 1441–1475).

**Dijkstra:** The real, currently-used implementation is `backend/logic/route_calculator.py:calculate_shortest_path()`, called from `POST /api/navigation/route` in `routes/navigation_routes.py`. It builds an adjacency list only from edges where `is_active` and `is_accessible` are true, adds the reverse direction only when `is_bidirectional` is true, and runs a standard heap-based Dijkstra with a `visited` set. A second, older implementation (`logic/route_logic.py`) exists and is only reachable from the deprecated `/route`, `/graph`, `/buildings*` endpoints (see §12).

**Route reaching the frontend:** `navigationApi.js:calculateRoute()` posts `{map_id, start_point_id, end_point_id}` to `/api/navigation/route` and returns the full `{path_point_ids, path_details, total_distance}` body untouched. `IndoorNavigationScreen.jsx` renders `path_details` (each a full `RoutePoint` including real `x`/`y`) as an SVG polyline overlaid on the map `<img>`.

**SVG/image coordinate alignment:** `RoutePoint.x`/`.y` are stored in the *original uploaded image's pixel space* (the value the admin clicked, `AdminMapScreen.jsx`, against `naturalWidth`/`naturalHeight` of whichever map image is being edited). `IndoorNavigationScreen.jsx`'s `RouteOverlay` (lines 141–204) re-projects those pixel coordinates onto the currently rendered `<img>` size with `(x / naturalWidth) * displayWidth`, so the overlay stays correct regardless of how large the `<img>` is rendered on screen. This is a real coordinate system, not invented data.

**Location codes as starting point:** `BarcodeEntryScreen.jsx` calls the public `GET /api/location-codes/resolve/{code}`, which re-validates the code is active and that its `RoutePoint`/`Map` still exist, then writes `{routePointId, mapId, buildingId, code}` to `localStorage["quickroute_start_location"]`. `IndoorNavigationScreen.jsx` reads that key, and only uses it as the start point if `resolvedStart.mapId === map.id` (the currently loaded map) — a code scanned for a different map is silently ignored rather than misapplied. If no valid resolved start exists, it falls back to the map's first `point_type: 'entrance'` RoutePoint.

**Roles/permissions:** `core/auth_deps.py` defines `get_current_user` (401 if missing/invalid JWT), `require_roles(*roles)` (403 if role not in the list), `require_any_admin`, `require_global_admin` (`super_admin`+`global_manager`), and `user_can_manage_building()`/`require_building_access()` for `building_manager` scoping via `user.building_ids`/`user.all_buildings`. Every mutating route file imports and applies one of these — enforcement is server-side, not just `RequireRole.jsx` on the frontend (confirmed by `backend/tests/test_api_integration.py`, e.g. `test_regular_user_cannot_create_building`, `test_unauthenticated_request_cannot_create_building`).

**Local vs S3 storage:** Local disk (`backend/uploads/maps/...`) is the default and requires no configuration. Setting `MAP_STORAGE_BACKEND=s3` plus `AWS_S3_BUCKET`/`AWS_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` in `.env` makes `services/storage_backend.py` additionally upload generated files to S3 and store the S3 URL on the `Map` document instead of the local `/uploads/...` URL; `boto3` is only imported when S3 mode is actually selected. A storage-sync failure falls back to the local URL rather than failing the upload (`storage_backend.py:97-106`).

## 5. Frontend Findings

**Authentication stack.** `AuthContext.jsx` is a single, clean source of truth: one storage key for the user (`quickroute_user`) and one for the token (`quickroute_token`), with an explicit code comment (`AuthContext.jsx:3-6`) noting the old dual `quickroute_user`/`quickroute_admin` key scheme was deliberately collapsed to one. `RequireRole.jsx` reads `isAuthenticated`/`isAdmin` from that context: unauthenticated → `/screen/02` (login); authenticated-but-not-admin → `/screen/15` (end-user home); admin role → renders the protected screen. `ADMIN_ROLES` = `super_admin`, `global_manager`, `building_manager` (`AuthContext.jsx:15-19`), matching the backend's `require_any_admin` set. `GET /api/auth/me` exists on the backend (`auth_routes.py:36-45`) but is **never called anywhere in the frontend** — session restore relies entirely on trusting the `localStorage`-cached user object from the last login/signup response, not re-validating the token against the server on app load. That means a token revoked or a role changed server-side after login will not be reflected in the UI until the user's next 401.

**API infrastructure.** `api/api.js` is the single shared JSON request helper (`apiRequest`): reads `API_BASE_URL` from `import.meta.env.VITE_API_BASE_URL` (currently `http://127.0.0.1:8000`, see `frontend/.env`), attaches `Content-Type: application/json` and `Authorization: Bearer <token>` (if a token exists) to every call, parses FastAPI's `{detail: "..."}` error shape on non-2xx responses, and clears both storage keys on a `401`. Every JSON-based API module (`authApi.js`, `buildingsApi.js`, `roomsApi.js`, `routePointsApi.js`, `routeEdgesApi.js`, `navigationApi.js`, `locationCodesApi.js`, `invitationCodesApi.js`) is a thin wrapper around this helper — no direct `fetch()`/axios calls exist in any screen or context except the map upload path. **`mapsApi.js:uploadMap()` (lines 98-119) is the sole exception**: because it needs `multipart/form-data`, it calls `fetch()` directly instead of `apiRequest()`, and in doing so it never attaches the `Authorization` header at all. This is the root cause of the reported bug — full trace in §9.

**Navigation state and refresh safety.** Screen-to-screen data (`building`, `destination`/`room`) is passed via React Router's `navigate(path, { state })`, which lives only in memory. A hard refresh on `DestinationSelectionScreen` or `IndoorNavigationScreen` loses that state — `IndoorNavigationScreen.jsx:215-216` reads `location.state?.building`/`location.state?.destination` and both silently become `null`, which the screen handles gracefully (shows `—` for destination, skips route calculation) rather than crashing, but the user has to navigate back and re-select. The one piece of navigation state that *does* survive a refresh is the scanned location code's resolved start point, which `BarcodeEntryScreen.jsx` persists to `localStorage["quickroute_start_location"]` — a deliberate and correct design choice, per the code comment at `IndoorNavigationScreen.jsx:18-21`.

**IDs passed between screens** are always the real MongoDB `id` strings coming back from the backend (`building.id`, `room.id`, `RoutePoint.id`) — I found no case of a screen inventing or hard-coding an ID.

**Admin screens.** `AdminDashboardScreen.jsx` and `AdminLocationsScreen.jsx`/`AdminRoomsScreen.jsx` are fully wired to `AdminContext.jsx`, which itself loads real data via `apiRequest`/`buildingsApi`/`roomsApi` on mount (`AdminContext.jsx:196-201`) and performs real create/update/delete calls. `AdminMapScreen.jsx` (the largest file in the app, ~3400 lines) is the actual graph-drawing tool: it implements map switching with a `refreshRouteGraph(mapId)` effect keyed on `selectedMapId` that explicitly resets `routePoints`/`routeEdges`/`draftPoints`/mode on every map change and on map delete/upload (`AdminMapScreen.jsx:623-709, 942-946, 1109-1113`), so switching maps does not leak state from another map — this matches the "no mixing" requirement. `AdminRoutesScreen.jsx` is a **separate, simpler CRUD screen** for `RoutePoint` only (no edges, no Test Route) that always sends `building_id: null, room_id: null` (`AdminRoutesScreen.jsx:362-363`), meaning a point created through this screen can never be linked to a room — it duplicates a subset of what `AdminMapScreen.jsx` already does more completely, and is a likely source of admin confusion (see §12 duplication).

**End-user screens** all load real data (`BuildingSelectionScreen.jsx` → `getBuildings()`; `DestinationSelectionScreen.jsx` → `getRooms({building_id})`; `IndoorNavigationScreen.jsx` → `getCurrentMap()`, `getRoutePoints()`, `calculateRoute()`). I found **no dummy/fallback route data anywhere in the active navigation path** — `utils/routeHelpers.js` carries an explicit comment (`routeHelpers.js:6-12`) stating it no longer contains hardcoded coordinates and that `data/routeData.js` was removed from the flow; that removal is confirmed by grep — `data/routeData.js` and `data/hospitalData.js` are not imported by any screen, context, or component (only `routeHelpers.js` itself references `routeData` in a comment).

**Cosmetic hard-coding.** `BuildingSelectionScreen.jsx:16` (`location: 'Rabin Medical Center'`) and `AdminDashboardScreen.jsx:19` (`campus: 'Rabin Medical Center'`), each duplicated across the `en`/`ar`/`he` translation blocks, render a fixed hospital-name badge regardless of which buildings/campus are actually loaded from the database. This is display text only — it does not affect any query, filter, or data — but it does violate the "must not be hard-coded to one specific building" intent at the UI level, and would visibly say "Rabin Medical Center" even if the database contains a completely different building set.

## 6. Backend Findings

**App wiring.** `app.py` registers routers in this order: `navigation_router` (includes the deprecated JSON endpoints, prefix-less), `auth_router`, `invitation_code_router`, `building_router`, `map_router`, `room_router`, `route_point_router`, `route_edge_router`, `location_code_router`. CORS (`app.py:54-63`) is hard-coded to `http://localhost:5173` and `http://127.0.0.1:5173` only — fine for local dev, but not configurable via `.env`, so any other deployment origin will be silently blocked by the browser until this is edited in code.

**Auth/JWT.** `core/security.py` hashes passwords with bcrypt (`passlib`), signs JWTs with `JWT_SECRET_KEY`/`JWT_ALGORITHM` (default `HS256`) and a `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` default of 1440 (24h) if unset in `.env`. If `JWT_SECRET_KEY` is absent from `.env`, `security.py:38-45` silently generates a random in-process secret — safe for a fresh dev clone (the app still starts) but means every token becomes invalid on process restart; this is a deliberate, commented trade-off, not a bug. `core/auth_deps.py:get_current_user` extracts the Bearer token from the `Authorization` header, decodes it, and re-fetches the `User` document from MongoDB on every request (not just trusting the payload) — a 401 (`INVALID_OR_EXPIRED_TOKEN`) is raised if the user no longer exists, which correctly handles a deleted user still holding an old token.

**Role/building-scope enforcement is real and server-side**, not merely a frontend convenience: every mutating route (`building_routes.py`, `room_routes.py`, `map_routes.py`, `route_point_routes.py`, `route_edge_routes.py`, `location_code_routes.py`) depends on `require_global_admin`, `require_any_admin`, `get_current_user` + manual role/scope checks, or `require_building_access`. This is exercised by `backend/tests/test_api_integration.py` (`test_regular_user_cannot_create_building`, `test_unauthenticated_request_cannot_create_building`, `test_building_manager_cannot_update_unassigned_building`), all of which assert on real HTTP status codes against the real route code.

**Two intentionally unauthenticated invitation-code endpoints exist** (`routes/invitation_code_routes.py`): `POST /api/invitation-codes/generate` (always issues a `regular_user`-role code) and `POST /api/invitation-codes/dev-create` (lets the caller pick **any** role including `super_admin`, and any `building_ids`/`all_buildings`). The file has an explicit, self-aware comment (`invitation_code_routes.py:17-25`) explaining this is a deliberate development-only gap because there's no bootstrap mechanism for the first admin account, and that `/dev-create` must be removed or gated before real deployment. This is accurate and is flagged again in §11 as a Critical security item.

**`POST /api/auth/register`** (`auth_routes.py:21-23`, `auth_logic.py:17-54`) is also unauthenticated and creates a `regular_user` account with no invitation code at all. It is exported from `authApi.js` (`registerUser`) but **never called by any screen** — confirmed by grep across `frontend/src`. It's a live, reachable API endpoint that bypasses the product's stated invite-only onboarding model, just not reachable through the UI.

**Maps.** `POST /api/maps/upload` (`map_routes.py:380-501`) accepts `.pdf/.png/.jpg/.jpeg/.webp` (enforced in `services/map_image_service.py:44-50` by extension, and checked again by content during PDF/image normalization — an invalid file raises `ValueError` → `400`), enforces a `MAP_MAX_UPLOAD_SIZE_MB` (default 50MB) streaming size cap during the chunked read (`map_image_service.py:224-260`, so oversized files are rejected without ever being fully buffered in memory), and processes the file in `BackgroundTasks` so the HTTP response returns immediately with `processing_status="pending"`. Scale is stored per-map (`scale`) and optionally per-floor (`floor_scales: {"0": 0.05, ...}`), consumed by `route_edge_routes.py:get_scale_for_floor()` when computing walkway distances from pixel distance. Map deletion (`map_routes.py:747-787`) **does** cascade-delete every `RouteEdge`/`LocationCode`/`RoutePoint` referencing that map (edges first, then location codes, then points — correct dependency order) and reassigns `is_current` to another map if the deleted one was current; this is confirmed by `test_map_deletion_cascades_to_points_and_edges`.

**Buildings**, by contrast, use *rejection* rather than cascade on delete (`building_routes.py:125-189`): deleting a building with any linked `Room`, `RoutePoint`, or `LocationCode` returns `409` with an explanatory message instead of silently deleting dependents. This is an intentional and reasonable asymmetry (buildings are a much bigger blast radius than a single map), but worth knowing it's inconsistent with map-deletion behavior when reasoning about "cascade" as a single concept.

**RoutePoints/RouteEdges.** Point deletion is rejected (`409`) if any edge references it or any `LocationCode` uses it as a start point (`route_point_routes.py:189-246`). Edge creation validates `map_id`/`from_point_id`/`to_point_id` exist, rejects `from_point_id == to_point_id`, and computes `distance` server-side from real pixel coordinates × floor scale for `walkway` edges (rejecting cross-floor walkways) or requires an admin-supplied `distance_override` for `stairs`/`elevator` edges (rejecting same-floor stairs/elevators) — confirmed correct in `route_edge_routes.py:83-149`. **No backend check exists for duplicate edges** (the same `from_point_id`↔`to_point_id` pair created twice via direct API calls) — de-duplication only happens client-side inside `AdminMapScreen.jsx`'s draw-save flow, not as a database constraint or route-level check. Likewise, **no duplicate-position check exists for RoutePoints** — two points can be created at the identical `(x, y, floor)` on the same map with no error.

**Navigation.** `POST /api/navigation/route` (`navigation_routes.py:139-214`) validates both points exist and both belong to the given `map_id` (400 if not), loads only that map's edges, and calls `calculate_shortest_path()`. A route that doesn't exist returns `404` ("No route found between the selected points") rather than a fake/empty route.

**Location codes.** `code` uniqueness is checked at the application layer only (`LocationCode.find_one(LocationCode.code == data.code)` before insert, `location_code_routes.py:141-144`) — there is no unique index in the `LocationCode` model's `Settings`, so two concurrent requests could theoretically both pass the check and insert duplicate codes (race condition, low likelihood in this workload but real). The public resolve endpoint re-validates the point/map still exist on every call (`location_code_routes.py:100-111`), so a code is never trusted blindly even after being created.

## 9. Current Map Upload Bug

**Exact request path traced:**

1. `AdminMapScreen.jsx:2493` — the Upload button's `onClick={uploadMap}` (a local handler, not the API module — same name, different scope).
2. `AdminMapScreen.jsx:1020-1096` — the local `uploadMap()` handler builds a `FormData` (`file`, `title`, `scale`, `use_openai`, optional `campus`/`address`/`description`) and calls `apiUploadMap(formData)` at line 1096, which is `uploadMap` imported from `../api/mapsApi` (aliased at `AdminMapScreen.jsx:14`).
3. `frontend/src/api/mapsApi.js:98-119` — this is the actual root cause. Unlike every other function in every other `api/*.js` module, this one does not go through `apiRequest()` (`api/api.js`) because that helper unconditionally sets `Content-Type: application/json`, which is wrong for `multipart/form-data`. Instead it calls `fetch()` directly:
   ```js
   const response = await fetch(`${API_BASE_URL}/api/maps/upload`, {
     method: "POST",
     body: formData,
   });
   ```
   This request has **no `Authorization` header at all** — `getStoredToken()`/`TOKEN_STORAGE_KEY` exist in `api/api.js` but are never referenced in `mapsApi.js`.
4. Request headers sent to the backend: `Content-Type: multipart/form-data; boundary=...` (browser-set) — no `Authorization`.
5. `backend/routes/map_routes.py:385-403` — `upload_map(...)` depends on `_admin: User = Depends(require_global_admin)`.
6. `require_global_admin` → `require_roles("super_admin","global_manager")` → `get_current_user` (`backend/core/auth_deps.py:33-63`) → `_extract_bearer_token(request)` (`auth_deps.py:24-30`) finds no `Authorization` header → returns `None` → `get_current_user` raises `HTTPException(**NOT_AUTHENTICATED)`.
7. `backend/core/errors.py:74-77` — `NOT_AUTHENTICATED = {"status_code": 401, "detail": "Not authenticated"}` — this is the exact string ("Not authenticated") you saw in the browser console, confirming the trace end-to-end.

**Root cause, stated plainly:** `mapsApi.js:uploadMap()` forgot to attach the JWT. It is not a token-storage-key mismatch (both `api.js` and `AuthContext.jsx` agree on `quickroute_token`), not a FormData-construction problem (the fields being sent match what `map_routes.py:upload_map()` expects via `File(...)`/`Form(...)`), and not a backend permission-configuration problem (`require_global_admin` is correct and consistent with every other map-mutating route). The token exists in `localStorage` exactly as you observed — it's just never read by this one function.

**Safest fix direction (not applied):** add the same `Authorization: Bearer <token>` header that `apiRequest()` already computes to the raw `fetch()` call inside `uploadMap()` in `mapsApi.js`, ideally by factoring a tiny shared "get bearer header object" helper out of `api.js` so both the JSON path and this multipart path stay in sync automatically instead of two independent implementations that can drift again.

**Related API modules that should be re-audited once this is fixed:** none of the other `api/*.js` modules bypass `apiRequest()`, so `mapsApi.js:uploadMap()` is the only function with this class of bug — confirmed by grepping `frontend/src` for `fetch(` and `XMLHttpRequest`, which returns only this one call site plus `api.js`'s own internal `fetch()` inside `apiRequest()` itself.

## 11. Security Findings

**Critical**
- `POST /api/invitation-codes/dev-create` is completely unauthenticated and accepts an arbitrary `role` (including `super_admin`) and arbitrary `building_ids`/`all_buildings` (`invitation_code_routes.py:59-100`). Anyone who can reach the backend can mint a `super_admin` invitation code and self-provision full admin access. The code itself documents this as a known, deliberate gap for local bootstrap — it must be removed or gated (e.g. behind a one-time setup flag, or simply deleted from a deployed build) before any real deployment.
- `POST /api/invitation-codes/generate` is also unauthenticated (mints `regular_user`-role codes only, so lower severity than `/dev-create`, but still lets anyone generate unlimited valid signup codes without any admin approval step).

**High**
- No unique index at the database layer for `users.email`, `invitation_codes.code`, or `location_codes.code` — all uniqueness is enforced by an application-level `find_one()` check immediately before insert (`auth_logic.py:18`, `invitation_code_logic.py:19`, `location_code_routes.py:141`). Under concurrent requests this is a race condition that could produce duplicate emails/codes; low likelihood in normal usage, but a real gap for anything beyond a single-admin demo.
- `POST /api/auth/register` bypasses the invitation-code system entirely and is reachable by anyone (not gated in the frontend, but live on the backend) — account-creation with no approval step, undermining the "admin manages users via invitation codes" model described in your spec.

**Medium**
- CORS origins are hard-coded to `localhost:5173`/`127.0.0.1:5173` (`app.py:56-59`) with no env-var override — not itself a vulnerability, but means the current code cannot be pointed at a real deployment origin without an in-code edit, which risks someone loosening it to `allow_origins=["*"]` under deadline pressure instead of doing it properly.
- No file-upload rate limiting or per-user upload quota — `MAP_MAX_UPLOAD_SIZE_MB` (50MB default) caps individual file size, but nothing stops an authenticated admin account (or a compromised one) from uploading unlimited files.
- `map_routes.py` error responses occasionally include raw exception text in `detail` (e.g. `f"Could not save the uploaded map: {error}"`, `map_routes.py:444`; `f"Could not create the map record: {error}"`, line 490) — this can leak internal file-path or library error details to the client. Not a secret-leak in the sense of credentials, but more detail than a production API should return.

**Low**
- `backend/.env.example` is a clean, secret-free template (confirmed by reading it) — good practice already followed. I did not open `backend/.env` itself, per the audit rules; I can only confirm the *names* of the variables it's expected to define (`OPENAI_API_KEY`, `MONGO_URI`, `DATABASE_NAME`, `MAP_STORAGE_BACKEND`, `AWS_S3_BUCKET`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `JWT_SECRET_KEY`, `JWT_ALGORITHM`, `JWT_ACCESS_TOKEN_EXPIRE_MINUTES`), matching what `core/security.py`, `database/mongo.py`, and `services/storage_backend.py` read via `os.getenv`.
- `frontend/` has no `.env.example` at all (only a real `.env`) — a minor onboarding gap, not a security issue by itself since the only variable there (`VITE_API_BASE_URL`) isn't secret.
- JWT expiry defaults to 1440 minutes (24h) if unset — reasonable for a demo, long for production; no refresh-token mechanism exists, so a stolen token is valid for its full lifetime with no revocation path beyond deleting the user.
- Password minimum length is 6 characters (`schemas/auth_schema.py:17,23,29`) — usable for a demo, weak for production.
- I found no path-traversal risk in map file handling: uploaded filenames are never used to construct output paths — the backend always generates its own `{map_id}.png`/`{upload_token}_upload{ext}` filenames (`map_image_service.py:220-222`, `map_routes.py:425`), and `map_id` values are either a `uuid4().hex` token or a real Mongo ObjectId, never user-supplied path segments.
